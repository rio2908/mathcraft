# Архитектура MathCraft

## 1. Общая модель

MathCraft — однопроцессное Pygame-приложение с ручной машиной состояний.
Статический контент, генераторы заданий и файловое хранение вынесены из
`main.py`; основной модуль координирует игровой сеанс и интерфейс.

```text
game_content.py: таблицы данных
  ↓
game_tasks.py: генераторы маршрута и заданий
  ↓
game_storage.py: чтение и запись JSON
  ↓
main.py: миграция профиля и состояние текущей сессии
  ↓
async main(): события → обновление → отрисовка → автосохранение
```

Основной цикл работает с частотой до 60 кадров в секунду. В конце каждого кадра
выполняется `await asyncio.sleep(0)`, чтобы браузерный runtime Pygbag получал
управление.

## 2. Модули

- `game_content.py` содержит только константы и таблицы: биомы, предметы,
  профили сложности, логические задачи, мобов и шаблоны маршрутов.
- `game_tasks.py` содержит генераторы без зависимости от Pygame: маршрут,
  сундуки, библиотекаря, адаптивные повторы и математические задания.
- `game_storage.py` отвечает только за чтение и запись
  `mc_math_save.json` и `mc_last_player.txt`, а также проверку переносимой копии.
- `game_backup.py` открывает системный выбор документа Android для экспорта и
  восстановления копии вне приватного хранилища приложения.
- `game_reminders.py` синхронизирует челленджи с нативными Android-напоминаниями
  и запрашивает разрешение на уведомления после действия взрослого.
- `android/src/.../reminders/` содержит Java-планировщик и `BroadcastReceiver`:
  они работают без запуска Python/Pygame, в том числе после закрытия игры.
- `game_music.py` синтезирует короткие оригинальные музыкальные петли для
  каждого биома без внешних файлов.
- `main.py` инициализирует Pygame, мигрирует профили, хранит состояние сеанса,
  рисует интерфейс и выполняет игровой цикл.

Внутри `main.py` остаются следующие крупные блоки:

1. Инициализация Pygame, шрифтов и синтезатора звука.
2. Загрузка профиля, миграция и правила изменения экипировки.
3. UI-примитивы и кодовая пиксельная отрисовка.
4. Глобальное runtime-состояние и прямоугольники кнопок.
5. Боевые и сервисные функции.
6. `async main()`:
   - обработка событий по `game_state`;
   - обновление движения, частиц и таймера;
   - отрисовка по `game_state`;
   - сохранение таймера.

## 3. Машина состояний

| Состояние | Назначение | Таймер идёт |
|---|---|---:|
| `REGISTER` | Создание профиля: имя, аватар и режим | нет |
| `LOGIN` | Последний игрок или список существующих профилей | нет |
| `PARENT_PIN` | PIN с экранной цифровой клавиатурой | нет |
| `PARENT_MENU` | Секретная кнопка настроек после PIN | нет |
| `CHALLENGE_SETTINGS` | Выбор профиля, название, цель и запуск челленджа | нет |
| `EMERALD_SETTINGS` | Установка баланса выбранного игрока после PIN | нет |
| `BACKUP` | Экспорт и восстановление сохранений Android | нет |
| `HELP` | Детская инструкция | нет |
| `MOB_CATALOG` | Каталог мобов по биомам | нет |
| `GAME` | Основной маршрут и задания островков | да |
| `MOB_BATTLE` | Бой со стражем биома | да |
| `SAGE_CHALLENGE` | Задача библиотекаря | да |
| `CHEST_LOCK` | Замок сундука после трёх чистых биомов | да |
| `REVIEW` | Итоги завершённого биома | нет |
| `BOSS_BATTLE` | Финальная битва с Драконом | да до победы |
| `FINAL_STATS` | Итоги текущего марафона | нет |
| `HISTORY` | Список сохранённых прохождений | нет |
| `HISTORY_DETAIL` | Ошибки выбранного прохождения | нет |
| `WORKBENCH` | Магазин и экипировка | нет |
| `CONFIRM_RESET` | Подтверждение сброса марафона | нет |
| `CONFIRM_EXIT` | Подтверждение выхода | нет |

При добавлении состояния необходимы как минимум две ветки в `main()`:
обработчик событий и отрисовка. Если состояние должно учитываться таймером, его
нужно добавить в `TIMED_GAME_STATES`.

`marathon_timer_is_active()` дополнительно исключает завершённый марафон и
экраны результатов встреч (победу/поражение у моба, ответ библиотекарю,
законченный замок сундука, победу над Драконом). Движение обновляется только
в `GAME`: открытие меню или верстака ставит переход между островками на паузу
и не может неожиданно запустить бой поверх другого экрана.

## 4. Координаты маршрута

- `TOTAL_QUESTS = 50`.
- `STEPS_PER_WORLD = 10`.
- `get_task_position()` преобразует глобальный номер задания в индекс биома и
  номер островка 1–10.
- Массив `platforms` сохраняет технический элемент с индексом 0 для удобной
  индексации, но он не отрисовывается. Игровые островки — только 1–10.
- Герой появляется непосредственно на островке текущего задания.
- После верного ответа он перемещается к следующему островку. После задания 10
  открывается экран итогов биома вместо движения к несуществующему островку 11.

## 5. Генерация заданий

`game_tasks.make_math_task()` возвращает кортеж:

```python
(display_question, correct_answer, choices, operation, clean_expression)
```

`clean_expression` сохраняется в статистике и используется Драконом. Примерно
25% обычных заданий скрывают один операнд (`7 + ? = 15`). Для способностей
некоторых мобов этот режим можно включить принудительно.

`make_task_for_step()` сначала проверяет `adaptive_tasks`. Если для текущего
островка назначено повторение, оно подменяет случайный пример. Иначе пример
создаётся из операций текущего маршрута.

`game_tasks.make_review_task()` восстанавливает задание из сохранённой ошибки и корректно
поддерживает как обычное выражение, так и выражение с пропущенным числом.
`game_tasks.make_nether_task()` создаёт двухоперационные примеры для всех
стражей Незера с диапазоном до 20 или до 100 согласно режиму профиля.
`make_mob_battle_task()` вызывает его при `kind == "nether_mixed"`; выражение
сохраняется в том же формате, что и обычные ошибки, для повтора у Дракона.

`pick_logic_task_with_history()` выбирает загадку библиотекаря из ещё не
показанных в текущем круге и возвращает обновлённую историю. Профиль хранит
`sage_seen_questions` отдельно по сложности и `sage_challenge` для возобновления
незавершённой встречи. Старые профили получают пустую историю при загрузке.

## 6. Маршрут марафона

`game_tasks.create_marathon_route()` один раз на марафон выбирает для каждого биома:

- одну из трёх тематических локаций;
- набор математических операций согласно сложности игрока;
- одного из мобов биома (обычно трёх, в ледяном биоме — четырёх);
- позицию моба с 3-го по 8-й островок.

Дополнительно создаются:

- сундук в следующем биоме после трёх чистых биомов подряд;
- одна позиция библиотекаря, не совпадающая с мобом и границей биома;
- до трёх адаптивных заданий следующего марафона.

Все эти значения сохраняются. Нельзя генерировать их заново при каждом запуске,
иначе содержимое незавершённой игры изменится.

`finish_biome()` фиксирует результат биома до перехода на следующий экран.
`biome_had_error` остаётся истинным после возврата в начало биома, поэтому
переигрывание не превращает его в чистый. Каждый третий чистый биом назначает
`chest_task` в следующем; если третьим был Край, используется
`chest_pending_next_marathon`. Награда и варианты ключей сохраняются в
`chest_challenge` до закрытия результата, поэтому повторный запуск не создаёт
нового содержимого.

## 7. Сохранения

### Файлы

- `mc_math_save.json` — словарь профилей по имени игрока;
- `mc_last_player.txt` — имя последнего явно выбранного игрока.

При первом запуске без сохранений открывается `REGISTER`; стартовое сохранение
не создаётся до подтверждения имени. При следующих запусках `LOGIN` показывает
последний выбранный профиль. Через «Сменить игрока» доступны остальные профили,
а через «Создать игрока» — регистрация нового. Список делится на страницы по три
профиля. Старые профили Ксении и Насти мигрируют без потери прогресса.

Оба пути сейчас относительные. На Android файлы попадают во внутреннее хранилище
приложения; при удалении приложения Android удаляет их. В браузере Pygbag
обслуживает файловые операции через BrowserFS. Синхронизации между окружениями
нет.

На экране регистрации и выбора игрока есть «Копия данных». Через системный
выбор файла Android она сохраняет всех игроков, историю и выбранного игрока в
JSON за пределами приватного каталога приложения. После переустановки файл
можно выбрать для восстановления. Совпадающие имена не перезаписываются, чтобы
не потерять более новый локальный прогресс. Автоматическое резервирование
Android включено, но зависит от настроек устройства и не заменяет эту копию.

`game_backup.AndroidBackupPicker` запускает системное окно на UI-потоке Android.
Имя `MathCraft-backup.json` передаётся через `Bundle.putString`, а не через
перегруженный `Intent.putExtra` (PyJNIus может выбрать `char[]` вместо строки,
из-за чего DocumentsUI предлагает `invalid.json`). Импорт допускает любой MIME:
формат проверяется по содержимому, поскольку файловые провайдеры по-разному
помечают JSON.

Открытие URI и ограниченное чтение/запись идут в фоновом потоке; очередь передаёт
результат в `poll()`. Локальные профили объединяются только в игровом потоке,
чтобы не потерять изменения, сделанные во время ожидания. Экспорт открывается
в режиме `wt`, обрезающем прежнее содержимое, и подтверждается лишь после
успешных записи, flush и закрытия. Дескрипторы закрываются и при ошибках.
При ожидании провайдера дольше 30 секунд показывается ошибка; опоздавший импорт
не применяется. Большая копия для экспорта освобождается, если провайдер ещё
не открыл файл. Повторная попытка разрешается только после выхода прежнего
I/O-потока: иначе зависший провайдер мог бы накопить неограниченное число
потоков, JNI-ссылок и дескрипторов. Если поток не вернулся, нужно перезапустить
приложение; вернуться в игру можно сразу. Системный блокирующий
вызов провайдера нельзя принудительно завершить Python-потоком, но он не
блокирует кадры игры. Пустые копии и файлы больше 10 МиБ отклоняются; экспорт
также проверяет размер до создания документа. Поддерживается UTF-8 BOM.

`game_storage.set_player_emeralds()` заменяет только баланс выбранного профиля,
сохраняет весь словарь игроков и проверяет результат записи. Экран
`EMERALD_SETTINGS` обновляет также текущий профиль в памяти; челлендж, история и
остальные профили не меняются. Ввод без нажатия «Применить» не сохраняется.

### Android-напоминания

После успешной атомарной записи `save_data()` вызывает `challenge_reminders.sync()`.
JNI вызывается только при изменении списка игроков или полей челленджа
(`active`, `name`, `last_date`), а не после каждого ответа/обновления таймера.
Нативный код хранит абсолютный путь к JSON во внутренних `SharedPreferences` и
перед уведомлением читает актуальное сохранение. Он не записывает профили и
не зависит от работающего Python-процесса. При ошибке напоминаний сохранение
игры остаётся действительным.

`AlarmManager.setAndAllowWhileIdle()` назначает два одноразовых события на
ближайшие будущие 07:00 и 17:00 в часовом поясе устройства. После доставки
события планируются заново по календарю, без прибавления фиксированных 24 часов.
День, уже зачтённый сегодня, и неактивный челлендж не вызывают уведомления.
Победа отменяет видимую карточку игрока; завершение последнего активного
челленджа также отменяет оба будильника. Карточка индивидуальна для каждого
игрока; вечерняя заменяет утреннюю. Дата отправки для каждой пары игрок/час
защищает от дублей. Напоминание старой даты или задержанное на два часа и более
не показывается, поэтому утреннее сообщение не появляется вечером или ночью.

`ReminderReceiver` восстанавливает расписание после `BOOT_COMPLETED`,
`TIME_SET`, `TIMEZONE_CHANGED` и `MY_PACKAGE_REPLACED`. Чтение файла вынесено из
потока Android UI через `goAsync()`. Receiver закрыт для сторонних приложений
(`exported=false`); его добавляет `android/p4a_hook.py` после генерации манифеста
p4a, перед Gradle-сборкой. Java-исходники подключены через `android.add_src`.

На Android 13+ разрешение `POST_NOTIFICATIONS` запрашивается при запуске
челленджа или кнопкой в секретном меню. Отказ не мешает игре и не вызывает
повторных запросов без действия взрослого. На старых Android отдельный запрос
не нужен, но системная блокировка уведомлений всё равно учитывается.
При возврате приложения на экран расписание обновляется без запроса разрешения,
чтобы изменения разрешения/канала в настройках телефона вступили в силу.
Специальное разрешение точных будильников не используется: ОС и экономия
батареи могут задерживать доставку. Принудительная остановка приложения
блокирует фоновые события до нового запуска. Сетевые сервисы не требуются.

### Основные группы полей профиля

| Группа | Примеры полей |
|---|---|
| Экономика | `emeralds`, `streak`, `last_date` |
| Игрок | `avatar` (`boy`/`girl`), `difficulty` (`easy`/`hard`), `hero_frog` |
| Прогресс | `task_num`, `marathon_elapsed_seconds` |
| Ошибки | `marathon_errors`, `marathon_error_details`, `boss_penalty_errors` |
| Снаряжение | `helmet`, `helmet_durability`, `artifacts`, `artifact_charges`, `disabled_artifacts`, транспорт, `disabled_vehicles`, `unicorn_equipped` |
| Расходники | `totems`, `luck_potions`, `luck_timer`, `strength_potions`, `food_apples`, `food_bread`, `hero_hearts` |
| Питомец | `pet`, `pet_errors`, `pets_lost` |
| Случайный маршрут | `marathon_route`, `sage_task`, `chest_task` |
| Серия сундука | `clean_biome_streak`, `biome_had_error`, `chest_pending_next_marathon`, `chest_challenge`, `chest_seen_questions` |
| Состояния встреч | `sage_completed`, `defeated_mob_worlds`, `strength_mob_task`, `frog_mob_task`, `web_seconds_left`, `vampire_bat_active`, `vampire_bat_target_world`, `heat_rune_task`, `heat_rune_seconds_left`, `heat_rune_mob_hp`, `heat_rune_regen_elapsed`, `sharp_sword_task`, `boss_artifact_choice` |
| Обучение | `adaptive_tasks`, `game_history` |
| Челлендж | `activity_challenge`: `name`, `target_days`, `count`, `active`, `last_date` |

`game_tasks.start_activity_challenge()` запускает челлендж явно, а
`credit_activity_day()` вызывается только в транзакции победы над Драконом.
Снимок результата помещается в `game_history[].activity_challenge` вместе с
историей прохождения и сохраняется одной записью с датой зачёта. Это позволяет
обнулить рабочий счётчик при выполнении и сохранить итог на экране победы после
перезапуска. Сброс марафона не затрагивает челлендж. Дата последнего зачёта
сохраняется даже при запуске следующего челленджа.

Ошибки мобов и Дракона через `record_battle_error()` включаются в общие
`marathon_errors` и `marathon_error_details`, но не увеличивают
`boss_penalty_errors`: здоровье Дракона усиливают только незащищённые ошибки
основного маршрута. Поле `source` в новых боевых записях равно `mob` или `boss`;
прежние записи без этого поля продолжают загружаться. Ошибки мобов входят в
очередь повторения Дракона и последующие адаптивные задания.

Новый марафон сбрасывает текущую серию правильных ответов вместе с таймером.
Финальное целое время фиксируется при победе и больше не перезаписывается
ожиданием на экране завершённой игры. Остаток Руны тепла записывается только
из текущего боя: закрытие приложения из меню не использует неинициализированные
боевые runtime-переменные и не стирает сохранённый эффект.

`get_player()` одновременно загружает профиль и выполняет миграцию. Новое поле
нужно добавлять в создание нового профиля и в ветку существующего профиля.
Миграции должны быть идемпотентными: повторная загрузка не должна повторно
начислять предмет или сбрасывать прогресс.

### Моменты записи

Сохранение выполняется после ответов, покупок, важных переходов, применения
предметов, каждые десять секунд активного таймера и при штатном выходе.
На Windows и Android новый JSON сначала записывается во временный файл рядом с
сохранением и затем атомарно заменяет прежний. Это не даёт другому потоку
прочитать частично записанный файл. В браузере BrowserFS используется прежняя
прямая запись из-за неподтверждённой поддержки `os.replace()`.

### Известные ограничения

- запись в браузере выполняется напрямую;
- ошибки чтения и записи подавляются общим `except`, логирования нет;
- нет автоматической облачной синхронизации и периодического экспорта;
- uninstall Android-приложения удаляет локальные данные;
- debug APK из разных CI-запусков может иметь разную подпись и не обновляться
  поверх установленной версии.

## 8. Боевая подсистема

### Мобы

`start_mob_encounter()` вычисляет здоровье и создаёт первое задание.
`MOB_ABILITIES` задаёт базовое здоровье и тип механики. `make_mob_battle_task()`
применяет способность к генерации примера.
У Ледяного голема `advance_mob_regeneration()` обновляет здоровье после каждого
кадра активного боя; правильный ответ сбрасывает четырёхсекундный отсчёт.
Ошибка у Ведьмы через `apply_witch_curse()` один раз включает `hero_frog` на
остаток марафона: максимум одно сердце, без эффектов предметов, транспорта и
питомца. `reset_entire_marathon()` снимает проклятие. Пещерный паук с
вероятностью 90% накладывает десятисекундную паутину; `web_seconds_left`
восстанавливается после перезапуска, а обратный отсчёт идёт внутри обычного
кадрового цикла без блокирующего ожидания.
У Магмового куба `mob_swap_seconds_left` отсчитывается только во время активного
боя и сбрасывается при новом примере. После обработки событий, но до отрисовки,
`rotate_visible_choices()` перемещает каждый видимый вариант на другую кнопку.
Скрытая Книгой позиция не трогается. Таймер и порядок кнопок не сохраняются:
при повторном входе бой начинает новый пример с полными тремя секундами.
Вампир выбран из пула Незера. `steal_emeralds()` ограничивает кражу текущим
балансом. После победы `vampire_bat_active` и `vampire_bat_target_world`
сохраняют сопровождающую мышь; `trigger_vampire_bat()` списывает до 10
изумрудов и выключает её при первой ошибке на любом игровом задании до
следующего стража. Чистая победа над следующим стражем также выключает мышь.
Жезл лягушки отключает вампирскую способность вместе с остальными.
Активный волк предотвращает появление сопровождающей мыши после победы над
Вампиром; `wolf_repels_vampire_bat()` удаляет уже активную мышь при покупке
волка. `get_player()` устраняет несовместимое сочетание волка и мыши в старом
сохранении. Проклятие Ведьмы выключает защиту волка.

Победа отмечает индекс биома в `defeated_mob_worlds`; только после этого моб
исчезает с маршрута. Поражение сбрасывает `task_num` к первому островку биома.
На последнем верном ударе запускается короткий визуальный взрыв и отрисовка
пепла, а кнопка продолжения становится доступна после основной фазы эффекта.

Позиция 50 в последнем биоме является клеткой Дракона. После завершения движения
на неё `is_final_boss_position()` сразу переводит игру в `BOSS_BATTLE`, поэтому
обычный пример основного поля на этой позиции не показывается.

Зелье силы сохраняет номер текущего задания в `strength_mob_task`. Благодаря
этому закрытие приложения посреди боя не расходует эффект впустую. После победы
или поражения поле очищается.
Жезл лягушки аналогично сохраняет `frog_mob_task`: повторный вход в бой
восстанавливает лягушку с одним сердцем, не списывая второй заряд. Применение
Жезла сбрасывает лечение, паутину и перестановку ответов, стирает их остатки
из сохранения и заменяет пример обычным; `start_mob_encounter()` очищает
возможные старые остатки эффектов у уже превращённого моба.
Руна тепла сохраняет номер встречи, оставшиеся секунды, здоровье голема и
прошедшую часть отсчёта лечения. В активном бою
с Ледяным големом `advance_heat_rune()` отделяет время паузы от времени,
которое передаётся `advance_mob_regeneration()`. Остаток Руны записывается
примерно раз в секунду и при штатном выходе; повторный запуск не списывает
новый заряд.
Заряды артефактов лежат в `artifact_charges`. Старым владельцам при миграции
выдаётся полная прочность без повторной покупки. `sharp_sword_task` и
`boss_artifact_choice` фиксируют уже оплаченный эффект встречи, поэтому
повторный вход после закрытия приложения не списывает ещё один заряд.

### Дракон

Здоровье вычисляется из базового значения, артефактов и числа незащищённых
ошибок. Очередь `boss_review_queue` содержит уникальные выражения из текущего
марафона. После исчерпания очереди используются случайные смешанные примеры.
Ошибка без тотема сбрасывает серию верных ответов босса до нуля.

## 9. Отрисовка и звук

Интерфейс проектируется в фиксированной системе координат `1000 × 600` и затем
масштабируется окружением. Кнопки представлены `pygame.Rect`, поэтому изменение
позиции должно синхронно учитываться в обработке клика и отрисовке.

Графика создаётся функциями `draw_*`. Нового моба нужно добавить как минимум в:

1. `MOB_POOLS`;
2. `MOB_ABILITIES`;
3. `draw_mob()`;
4. каталог и документацию, если механика новая.

`draw_world_background()` рисует статический рельеф и небольшое число
анимированных декоративных элементов для каждой из 15 локаций. Анимация
вычисляется из общего `anim_tick` и не хранит отдельные растущие коллекции
частиц.
`draw_mob()` рисует моба без отдельного светящегося фона; видимость на разных
локациях обеспечивается контрастными цветами частей самого персонажа.

Звук синтезируется `ensure_audio()` после первого пользовательского жеста — это
ограничение браузерного autoplay. Не инициализируйте аудио принудительно раньше.
Фоновая тема текущего биома создаётся при первом воспроизведении и запускается
на зарезервированном канале микшера. Эффекты ответов используют остальные
каналы. `sync_biome_music()` включает музыку только в активных игровых
состояниях и останавливает её при выключении звука или переходе в меню.

## 10. Память и время жизни объектов

- `biome_music_sounds` содержит не более пяти мелодий, `game_sounds` — пяти
  эффектов. Это намеренные кэши. При стандартном микшере 44,1 кГц/stereo пять
  музыкальных PCM-буферов занимают около 7,6 МиБ, а не растут с каждым биомом.
- Частицы и всплывающий текст удаляются по окончании срока жизни на всех экранах,
  включая меню. Поверхности текста/портрета не складываются в растущую коллекцию.
- Прямоугольники выбора игроков хранятся только для видимой страницы; смена
  страницы очищает старые записи, не удерживая имена и Rect всех просмотренных игроков.
- Android-подписка на результат выбора файла и UI-runnable создаются один раз на
  долгоживущий экземпляр bridge. Экспорт/импорт имеет не более одного живого
  I/O-потока, даже после тайм-аутов.
- В p4a `v2024.01.21` реестр `_RequestPermissionsManager._callbacks` сам не удаляет
  завершённые callback. После обработки результата `game_reminders.poll()` удаляет
  **только собственные** записи из этого реестра. Чужие callback и рабочая
  Java-подписка не затрагиваются. Это адаптация к зафиксированной версии p4a;
  при её обновлении нужно перепроверить устройство реестра.
- `game_history`, текущие ошибки и профили — сохраняемые пользовательские данные.
  Их рост при новых прохождениях ожидаем и не исправляется удалением истории.

Нагрузочный тест в `tests/test_memory.py` прогревает графику и звуки, затем
повторяет одинаковую нагрузку на 18 состояниях с фиксированной историей,
перезапусками марафона и большим числом эффектов. Он проверяет плато Python-кучи
через `tracemalloc`, а на Windows — ещё и private bytes/RSS, включая нативные
SDL-буферы. Проверка на ПК не доказывает отсутствие утечек Java/JNI на устройстве:
для этого отдельно нужен Android memory profiler.

## 11. Направление дальнейшего рефакторинга

Первый этап декомпозиции завершён: контент, чистые генераторы и низкоуровневое
хранение находятся в отдельных модулях. Следующие безопасные шаги:

1. добавить атомарную запись сохранений и версию схемы в `game_storage.py`;
2. вынести функции отрисовки без изменения координат;
3. выделить обработчики отдельных состояний игрового цикла;
4. только затем заменять глобальное состояние объектом `GameSession`.

Не начинайте большой рефакторинг одновременно с изменением игрового баланса:
это усложняет проверку совместимости сохранений и поведения мобильного UI.
